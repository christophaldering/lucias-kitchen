ZIEL
Etappe 1 von 3: Filter serverseitig umsetzen. Der Client uebergibt
die Filter als Query-Parameter statt im Browser zu filtern.
Die Sortierung bleibt in dieser Etappe unveraendert im Client.
Der Hintergrund-Vorlader bleibt in dieser Etappe ebenfalls drin.

TEIL 1 — SERVER
Datei: artifacts/api-server/src/routes/recipes.ts

GET /recipes akzeptiert zusaetzlich diese Query-Parameter.
Fehlt ein Parameter, wird nicht danach gefiltert.

  category   exakter Vergleich auf recipes.category
  time       "unter30" -> Minuten < 30
             "unter60" -> Minuten < 60
             Rezepte OHNE Zeitangabe werden dabei AUSGESCHLOSSEN
             (repliziert parseTotalMinutes -> Infinity)
  season     Wert muss im Array recipes.seasons enthalten sein
  cooked     "gekocht"     -> cooked_count > 0
             "nicht"       -> cooked_count = 0 ODER NULL
  photoType  "none" -> image_url IS NULL
             "ai"   -> is_ai_generated = true
             "scan" -> image_source = 'web' AND is_ai_generated
                       ist nicht true AND image_url IS NOT NULL
             "own"  -> image_url IS NOT NULL AND is_ai_generated
                       ist nicht true AND image_source ist nicht 'web'
  variants   "true"  -> keine Einschraenkung
             sonst   -> parent_recipe_id IS NULL
  chefPick   "true"  -> chef_pick = true

Das Zeitparsing ist identisch zu dem in der Route /recipes/stats.
Die Logik dort in eine wiederverwendbare SQL-Hilfsfunktion ziehen
und an beiden Stellen nutzen.

Alle Filter werden in getRecipesWithIngredients ergaenzt, sowohl
in der COUNT-Abfrage als auch in der Datenabfrage. total muss
die gefilterte Menge zaehlen, nicht die Gesamtmenge.

WICHTIG — Cache-Key erweitern
recipeListCacheKey beruecksichtigt bisher nur userId, filter, page
und limit. Alle neuen Parameter MUESSEN in den Key einfliessen,
sonst liefert der Cache falsche Ergebnisse.
